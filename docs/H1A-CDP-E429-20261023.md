La exportación HTTP, verificación y restauración no comenzaron. El run sigue BLOCKED; la corrección anterior del 503 sigue sin prueba alojada.

## Evidencia retrospectiva y límite

El intervalo `after-login` contiene 27 respuestas `200:preview`, una `303:preview`, dos `204:external`, un evento `cdp-failure-request-other-xhr` y un `pinned-origin-request-failed`; no registra fallos de petición ni errores de consola. La fila `h1a-navigation-intercept` original dice PASS y la fila siguiente `h1a-navigation-step` BLOCKED, ambas con `httpStatus=null`. La primera es una clasificación defectuosa del registro, no un PASS de interceptación. La capa final de `createWindowLedger()` descartó fase, clase de petición, destino, respuesta y disposición aunque el orquestador los enviaba. Solo puede afirmarse que un XHR de clase de ruta `other` falló en la etapa CDP `request` durante login. No puede identificarse retrospectivamente su origen ni distinguir construcción de cabeceras, `Fetch.continueRequest` o `Fetch.failRequest`; los 204 externos no acreditan que fueran la petición fallida. El deployment original está retirado y sus logs no están disponibles.

## Cambio acotado y reproducción

El callback ahora asigna una etapa enumerada a clasificación de URL/origen/redirección, construcción de cabeceras y las tres operaciones `Fetch`; una excepción conserva la etapa en un diagnóstico cerrado y continúa bloqueando la petición. Las dos capas del ledger retienen únicamente fase, clase de petición, destino, respuesta, disposición y operación de sus allowlists; el fallo de interceptación se registra BLOCKED. No se guardan URL, cabeceras, mensajes CDP, tokens ni secretos. Una inyección local de rechazo CDP en un XHR reproduce el bloqueo y acredita que el nuevo ledger distingue `CONTINUE_REQUEST`; las inyecciones de URL, cabeceras, respuesta y fallo de bloqueo prueban las demás etapas. Esa reproducción no demuestra cuál ocurrió en el run alojado: no se cambia el tratamiento de XHR, SSO, origen ni TLS por una hipótesis.

También se descubrió un residuo real del teardown: el módulo de retirada enumeraba ocho variables y omitía `RUBIK_RECOVERY_SCHEMA_ATTESTATION`, añadida después. Se retiró la novena variable del run de forma acotada y se unificó el teardown con `Get-U03WindowVariableNames` (nueve nombres). PowerShell 5.1 ejecutó la prueba de retirada idempotente. Una lectura SQL independiente del Preview exacto `rhnnplewqsekrnaousyl` confirmó usuarios, organizaciones, membresías, proyectos, auditoría, resultados, imports, invitaciones, idempotencia y outbox total/pending a cero; rol, políticas y sesiones temporales cero; escritor general NOLOGIN. La CLI confirmó variables de rama cero, deployment anterior ausente y vault DPAPI ausente.

Pruebas locales: tramo de navegación/CDP con fallo inyectado y ledger de ventana; recorrido H1-A local completo con HTTP de exportación, verificación offline, rechazo de manipulación y restauración doble en un segundo stack N1, con ambos stacks retirados. Esta evidencia no atribuye causa al run histórico ni cierra H1-A.

El login necesita los fixtures del recorrido; un preflight sin ellos solo acredita protección y transporte, no reproduce el XHR del run. No se aprovisiona una ventana nueva hasta tener un diagnóstico que justifique el intento y contención revisada. H1-A, R1, H1-B/U04, H1 global y H2 siguen abiertos.

## Diagnóstico y corrección

El código del run ocultaba stderr del restaurador hijo y reducía cualquier salida no PASS a `PREVIEW_EXPORT_LOCAL_RESTORE_FAILED`; por ello **no se puede atribuir retrospectivamente** el fallo alojado a una etapa interna concreta. La reproducción local con un manifiesto firmado por el endpoint HTTP real mostró dos defectos consecutivos del mismo hijo:

1. `LOCAL_RESTORE_DESTINATION_NOT_EMPTY`: `docker exec -i ... psql` recibía `input` con `stdio[0]='ignore'`, así que la consulta de conteos no se ejecutaba. La regresión falló antes de corregirlo.
2. `LOCAL_RESTORE_CONTENT_OR_SIGNATURE_MISMATCH`: tras habilitar stdin, el hijo comparaba las filas completas de PostgreSQL con las columnas exportadas. La prueba local existente ya seleccionaba las columnas del contrato; el hijo ahora hace la misma proyección antes de comparar hashes. La segunda ejecución de la regresión falló antes de esta corrección.

El SHA funcional `4df694a` transmite SQL por stdin, compara contenido y firmas sobre columnas equivalentes, registra `h1a-local-double-restore ATTEMPTED/BLOCKED` con un código cerrado del hijo y conserva el error original aunque falle el ledger. El wrapper PowerShell 5.1 informa la primera fila FAIL/BLOCKED y si hubo fixtures; ya no afirma falsamente que no hubo fixtures después de una campaña. Los mensajes libres del hijo, PostgreSQL y CLI no se publican.

## Contrato que debe respetar el operador

El flujo existente de producto es la única fuente de firmas:

- Auditoría: `appendTrustedAudit` construye y firma el evento en servidor, tras verificar la sesión y la membresía viva mediante `private.audit_writer_actor`.
- Resultados: `storeTrustedProviderResult` recibe solo un resultado emitido por el Core en el proceso servidor, lo firma con `serverKeyring`, persiste y verifica contenido/alcance. Para los fixtures se usa un adaptador de transporte sintético local al proceso; no se llama a Google ni OpenSEO y la evidencia se etiqueta como `synthetic-provider-result`.
- Imports: UI `uploadImport` + `imports` Data API activan el trigger `queue_import_insert`; el recibo `import.file` se firma con `processAuditOutbox`. Borrado legítimo debe procesar `import.erase` antes de limpiar proyecto.
- Exportación: ruta HTTP firmada existente; antes de entregar el manifiesto exige auditoría/outbox coherentes. Se registra status y hash del artefacto, no contenido sensible.
- Restauración: verificador offline valida manifiesto/firma y dos restauraciones se aplican a un stack local aislado recién creado, verificando idempotencia. El resultado de restauración queda claramente separado del origen Preview.

Las filas de `audit_events`, `provider_results`, `imports`, membresías y outbox se limpian por los IDs del ledger mediante los flujos autorizados. Nunca se inserta HMAC por SQL ni se borra directamente un recibo pending. Una lectura SQL independiente al final acredita IDs propios ausentes, inventario global de fixtures cero y outbox total/pending cero.

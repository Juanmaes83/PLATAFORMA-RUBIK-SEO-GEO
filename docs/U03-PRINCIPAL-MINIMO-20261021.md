# U03: principal de firma acotado a una ventana

## Contrato comprobado

El run alojado `f6350df4-dca0-4d46-9d24-d65b7699495d` se detuvo antes de instalar el rol. Una lectura posterior del Preview confirmó RLS 4/4 y que `rubik_audit_writer` ejecuta cuatro funciones `SECURITY DEFINER`: `audit_writer_actor`, `audit_writer_project`, `google_capture_command` y `openseo_job`. Las dos últimas proceden de grants de N1 para el escritor de producto. Un login con `SET ROLE rubik_audit_writer` hereda las cuatro; cambiar contraseña o login no restringe su capacidad efectiva.

`x-rubik-u03-run-id`, slugs, cookies y JWT son entradas del cliente. No conceden escritura por sí solos. La aplicación exige el HMAC del secreto exclusivo del deployment protegido, vinculado a ID, host, SHA, rama, run, scope y caducidad; Auth y membresía se vuelven a comprobar en el servidor. En PostgreSQL, la contraseña separada solo existe para `rubik_preview_u03_writer` y el administrador instala su comentario de run y políticas limitadas a `{u03-<run>-a/{a1,a2},u03-<run>-b/b1}`. Las políticas comprueban `rolcanlogin` y `rolvaliduntil` en cada sentencia, por lo que NOLOGIN y caducidad cierran también una sesión ya abierta. La conexión de ventana ya no lleva `options=-c role=rubik_audit_writer`; `SET ROLE` a ese escritor recibe `42501`. Los grants del producto y las dos RPC de proveedores no se modifican.

## Evidencia local nueva

- Dos stacks desechables N1 27/27, fuente y destino de restauración, sin Supavisor local. El principal inicia `NOLOGIN`, no hereda otro rol, no tiene `BYPASSRLS` ni uso de `auth`, y tiene exactamente dos funciones `SECURITY DEFINER` efectivas. Las RPC de OpenSEO y Google son **no ejecutables** por privilegio efectivo, incluso considerando `PUBLIC` y membresías. La comprobación usa `has_function_privilege` y una conexión como el propio rol.
- Run local de filas firmadas `f2b1eff8-95f7-4482-84d5-cacba318e4ab`, ledger `test-results/u03-window-principal-signed.jsonl`: auditoría, resultado sintético e import creados por flujos reales; propietario A lee y verifica firmas; B no lee las filas de A; escritura con firma real fuera del run rechazada (`42501`); recibos procesados y reintento idempotente. Con una sesión aún abierta, una caducidad administrativa impide leer la fila poblada e insertar el siguiente evento firmado; `NOLOGIN` vuelve a impedir la lectura tras reactivar temporalmente el rol. El run anterior `197f19da-dd47-4863-b419-5f32d1b805d8` conserva su evidencia previa sin atribuirle la última comprobación.
- HTTP local por socket y restauración a segundo stack: prueba dirigida `tests/integration/u03-window-http-restore.integration.test.ts` PASS; respuesta 200, firma/manifiesto válidos, copia alterada rechazada, restauración doble idempotente. Esta ejecución local no acredita H1-A alojado.
- Lectura SQL independiente final, antes de retirar los stacks: fuente con Auth, organizaciones, proyectos, auditoría, resultados, imports, idempotencia, outbox total/pending, rol, políticas y sesiones temporales a cero; destino también a cero. El escritor general quedó `NOLOGIN`. Ambos stacks propiedad de la prueba fueron retirados.
- Pruebas de operador con fallos simulados de preflight, instalación, activación, pooler, contención, allowlist/ledger y cleanup; PowerShell 5.1 real con datos ficticios para DPAPI y transporte. Las simulaciones acreditan orden y fail closed; la prueba SQL local acredita los permisos efectivos y no el pooler alojado.

## Operación alojada aún pendiente

El operador requiere ref Preview exacto, 27 migraciones, centinela, registro cerrado, inventario/outbox inicial a cero, escritor general bloqueado, deployment Vercel protegido con ID/host/SHA exactos y lote DPAPI branch-specific atestado por HMAC. Una conexión administrativa independiente instala el rol `NOLOGIN`, prueba contención, lo activa con TTL corto y una conexión **nueva** por Session pooler con TLS/CA/hostname verificados debe demostrar `session_user=current_user=rubik_preview_u03_writer`, grants efectivos, dos definers y denegación de ambas RPC. Si falla, `finally` ejecuta NOLOGIN, termina solo sesiones de ese rol, verifica la ausencia de nuevas conexiones y conserva ledger/IDs. Con inventario/outbox cero, revierte función, políticas, grants y rol; con residuos queda bloqueado y no los elimina manualmente.

**No se ejecutó SQL ni se creó fixture en Preview en este corte.** El Session pooler local continúa BLOCKED por entorno; PostgreSQL directo no lo sustituye. El código no tiene aún un deployment del nuevo SHA ni un lote branch-specific atestado. Hasta verificar ambos y el Session pooler del nuevo principal, I-2/I-5 alojados y H1-A alojado siguen BLOCKED. El PASS local no se presenta como PASS del Preview. Los ledgers alojados previos permanecen intactos.
